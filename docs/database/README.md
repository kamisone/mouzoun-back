# Mouzoun database

PostgreSQL 16+ (production and CI run 17; migrations are verified up → down → up on 16 and 17).
The schema lives in `migrations/` as reversible sqlx migrations; the Rust models mirror it in
`src/db/` (one module per section) and every query is checked at compile time (`query!` /
`query_as!`) against the committed `.sqlx/` metadata.

| Migration | Section |
|---|---|
| `0001_foundation` | extensions (citext, btree_gist, pg_trgm, unaccent), `set_updated_at()`, locales, currencies, exchange rates |
| `0002_identity` | users, roles, permissions, sessions, auth tokens, settings |
| `0003_media` | media folders, assets (+ translations), galleries |
| `0004_taxonomy_places` | categories, tags, amenities, places, farm crops |
| `0005_catalog` | products (+ accommodation types, activities, extras, packages), itineraries, relations |
| `0006_pricing` | guest categories, cancellation policies, rate plans, seasons, prices, taxes, promotions |
| `0007_inventory` | units, inventory calendar, activity schedules & slots, resources, closures |
| `0008_bookings` | customers, bookings, items, allocations, assignments, payments, refunds, invoices |
| `0009_content` | reviews, pages & blocks, menus, FAQs, banners, redirects |
| `0010_operations` | inquiries, newsletter, email templates & log, outbox, audit log |
| `0011_updated_at_triggers` | one `<table>_set_updated_at` trigger per table that has `updated_at` |
| `0012_seed` | reference data: locales, currencies, guest categories, permissions, roles, settings |

## Running migrations

```bash
cargo install sqlx-cli --no-default-features --features postgres,rustls   # once

sqlx migrate run                 # apply pending migrations (uses DATABASE_URL)
sqlx migrate revert              # undo the latest one (repeat to go further down)
sqlx migrate add -r <name>       # new reversible pair: NNNN_<name>.up.sql / .down.sql
```

The API applies pending migrations at startup unless `DATABASE_RUN_MIGRATIONS=false` (use that
when migrations are run as a separate deploy step). Migrations run while the previous release is
still serving: keep them backward compatible (add first, drop in a later release).

**After any change to a migration or a query**, regenerate the offline metadata and commit it:

```bash
sqlx migrate run && cargo sqlx prepare -- --all-targets --all-features
```

CI and the Docker build compile with `SQLX_OFFLINE=true`: a query that no longer matches the
schema, or stale `.sqlx/` files, fail the build.

Demo content for development (fr/en/ar products, places, prices, home page, menus, FAQs):

```bash
SEED_ADMIN_EMAIL=admin@mouzoun.test SEED_ADMIN_PASSWORD='a-long-password' cargo run --bin seed_dev
```

It refuses to run twice; reset the database to seed again
(`sqlx database drop -y && sqlx database create && cargo run --bin seed_dev`).

## Conventions

- Primary keys are UUIDv7 generated by the application (`Uuid::now_v7()`); append-only logs
  (`outbox_events`, `audit_logs`, `email_log`) use `bigint` identities.
- Every mutable table has `created_at` / `updated_at` (`timestamptz`); content tables add
  `deleted_at` (soft delete — queries filter `deleted_at IS NULL`).
- Statuses and kinds are `text` + `CHECK (... IN (...))`, mirrored by Rust enums declared with
  `text_enum!` in `src/db/`. `tests/it/schema.rs` fails if a CHECK list and its enum drift apart.
- Translatable entities have an `x_translations` table, primary key `(x_id, locale)`; slugs are
  `UNIQUE (locale, slug)`. Reads fall back field by field to the default locale.
- Money is stored in minor units (`*_minor bigint`, always with a currency column) and handled
  as `Money` in Rust; never floats, never major units. A column holds one unit only: a deposit
  is `deposit_percent` **or** `deposit_amount_minor` + `deposit_currency` (promotions:
  `discount_percent` / `discount_amount_minor` / `discount_free_nights`), decoded into the
  `Deposit` / `Discount` enums; CHECKs make the other combinations impossible.
- Human numbers: booking references `MZ-<yy>-<000123>` and invoices `<yyyy>-<000001>` restart
  every year from per-year counter rows (`booking_reference_counters`, `invoice_counters`).
- Codes and emails are `citext`; ranges use `daterange` / `tstzrange` with `[start, end)` bounds,
  and double bookings are made impossible by `EXCLUDE USING gist` constraints.
- Timestamps are UTC (`timestamptz`); local dates and times are the camp's, converted only in
  Rust by `crate::camp_time` (bundled IANA data: Morocco is UTC+0 since 20 September 2026).
  SQL never uses `AT TIME ZONE`, so a database with older tz data cannot disagree.

## The `updated_at` trigger rule

`0011_updated_at_triggers` attached `set_updated_at()` to every table that existed at that time.
**Every table created later must add its own trigger in the same migration:**

```sql
CREATE TABLE things (
    id uuid PRIMARY KEY,
    -- ...
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE TRIGGER things_set_updated_at BEFORE UPDATE ON things
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

(`DROP TABLE` in the down migration removes the trigger with it.) `tests/it/schema.rs` checks that
every table with an `updated_at` column has the trigger.

## Adding a language

Languages are data, not code: no migration is needed.

1. `INSERT INTO locales (code, name, native_name, is_rtl, is_active, sort_order)
   VALUES ('es', 'Spanish', 'Español', false, true, 4);`
2. Add the `es` rows to the `*_translations` tables as content gets translated. Missing fields
   fall back to the default locale (`locales.is_default`), so a partially translated language
   is safe to activate.
3. Front: add the locale to `nuxt.config.ts` (`i18n.locales`) and `i18n/locales/es.json`.

Public reads pick the locale from `?locale=`, then `Accept-Language`, then the default
(`services::locale::resolve_locale`); responses list the slugs of every other language
(`alternates`) for `hreflang` links.

## Adding a product kind

Products use class-table inheritance: `products` holds what every kind shares (status, SKU,
translations, categories, prices), and one table per kind holds the rest, linked by a composite
foreign key `(product_id, kind) → products (id, kind)` so a row can only extend a product of its
own kind.

To add e.g. `vehicle_rental`, in a new migration:

1. Widen the CHECK: `ALTER TABLE products DROP CONSTRAINT products_kind_check, ADD CONSTRAINT
   products_kind_check CHECK (kind IN ('accommodation', 'activity', 'extra', 'package', 'vehicle_rental'));`
2. Create the detail table:
   ```sql
   CREATE TABLE vehicle_rentals (
       product_id uuid PRIMARY KEY,
       kind       text NOT NULL DEFAULT 'vehicle_rental' CHECK (kind = 'vehicle_rental'),
       -- kind-specific columns...
       created_at timestamptz NOT NULL DEFAULT now(),
       updated_at timestamptz NOT NULL DEFAULT now(),
       FOREIGN KEY (product_id, kind) REFERENCES products (id, kind) ON DELETE CASCADE
   );
   ```
   plus its `updated_at` trigger (see above).
3. Add the variant to `ProductKind` in `src/db/catalog.rs` and a model struct for the table.
4. If it is bookable, add a booking service next to `services/booking/{accommodation,activity}.rs`
   (inventory, locking order, pricing via `services::pricing`).

## Outbox

Side effects (emails, cache invalidation) never run inside a business transaction. The
transaction writes an `outbox_events` row instead (`services::outbox::enqueue(tx, &Event::...)`),
so the event exists **if and only if** the change was committed; payloads carry ids only.
A trigger NOTIFYs the dispatcher on insert; failures retry with backoff, then the event is dead
(`failed_at`) until replayed; `dedupe_key` makes scheduled events unique. Everything about the
dispatcher, the handlers and the emails is in [`docs/email/README.md`](../email/README.md).

## Background jobs

| Job | Period | Does |
|---|---|---|
| `booking_holds` | 60 s | expires unpaid holds past `hold_expires_at`, releases inventory |
| outbox dispatcher | on NOTIFY + every `OUTBOX_POLL_SECS` | runs the handlers of due outbox events (`src/worker`) |
| email scheduler | 5 min | plans pre-arrival and review-request emails |
| `inventory` | 24 h | extends the inventory calendar to 18 months and activity slots to `booking.max_days_ahead`; never overwrites existing rows (manual overrides are kept) |
| `media_cleanup` | `MEDIA_CLEANUP_INTERVAL_SECS` | deletes objects of uploads never completed |
